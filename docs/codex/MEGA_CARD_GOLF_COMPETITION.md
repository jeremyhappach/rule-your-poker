## Ownership and reuse

- `src/lib/megaCardGolf/engine.ts` remains the shared versioned rule reducer.
  `competition.ts` admits a single hole and sequences subsequent admissions;
  legal actions, scoring, card values, deck generation and gameplay clocks use
  the same implementation as Arcade. Historical versions remain supported.
- `server/megaCardGolf/multiplayer.ts` owns live participant sequencing through
  typed intents. `api/mega-golf.ts` verifies Auth before using service-only RPCs.
  Private decks and future holes are never projected to browser clients.
- Live setup freezes the selected current course revision, rule version, hole
  count, human roster and consented stake. The enabled rule registry is the same
  registry consulted by Arcade. Course and 3/6/9/18-hole defaults are editable.
- The existing Golf settlement, stake consent, ante bridge, roster liability,
  whole-chip tie split, snapshots and continuation pattern is reused. Its
  gameplay/dealing engine is not copied. Normal Golf's rule core is unchanged.
- `server/delayed/adapter.ts` uses the same single-hole adapter. Existing children,
  attempts, outcomes, immutable review boards, per-viewer acknowledgements,
  36-hour availability/24-hour last call, notifications and parent settlement
  remain the async owners. No Mega-specific async tables or notification service.
- `MegaCompetitionBoard`, `MegaHoleReplay` and `MegaCompetitionScorecard` reuse
  the Arcade card/presentation path, Golf pencil glyphs, canonical fullscreen
  slots, sounds/mute, chip transport and winner announcement infrastructure.
  Pending scoring survives the next actor's snapshot. Replaying a saved hole
  cannot invoke a gameplay intent. Interrupted unseen replay restarts, and Skip
  Animation acknowledges the existing immutable event. Own and acknowledged
  opponent hole results populate the expandable scorecard.
- `Game.tsx` uses the existing terminal retention hook and local Session Ended
  admission. A connected client retains its result while canonical transport
  completes; a fresh already-ended session retains the existing lobby behavior.

accepts an absent new claim RPC during pre-registration rollout; other RPC
failures remain failures. New modes must stay closed until the matching API,
client, recovery worker and hosted proofs are verified together.
