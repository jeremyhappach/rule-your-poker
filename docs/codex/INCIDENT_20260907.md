## Capacity evidence and interpretation

The authenticated Supabase infrastructure dashboard confirms Free-plan
`t3a.nano`, up to 0.5 GB RAM, shared CPU, 60 database connections. The
database itself is approximately 153 MB and disk usage approximately 23%,
so disk capacity is not exhausted. No recent database restart occurred.

The database dashboard's 08:58pm-09:58pm CDT report shows substantial
persistent swap, growing during the incident, and large CPU-chart spikes
dominated by IOwait at the same late-window times as the RPC and cron
failures. Memory commitment also rises sharply during that interval. These
charts, varied slow tasks, and inability to start cron workers strongly
support host memory/I/O pressure as a shared contributor. They do not
identify the initiating process or prove that capacity is the only cause.

The September 6 telemetry retirement is present in the published build.
Historical aggregate boundary-RPC counts alone do not establish fresh
request amplification tonight. The organization quota banner describes
restrictions starting September 30, not a current restriction; observed
errors are not HTTP 402.
